## HIGH

### 1. Festival broadcast imports non-existent module functions — sends nothing, reports "completed"
- **File:** `rotation_engine.py:494` (and `:499`)
- **What's wrong:** `from whatsapp_engine import queue_message` / `from email_engine import queue_email` — both are *instance methods* (`whatsapp_engine.py:384`, `email_engine.py:416`), no module-level function exists. Import raises `ImportError` on the first contact; kwargs (`to=`, `template=`, `body=`) are also wrong.
- **Why silent:** Wrapped in `except Exception: stats['failed'] += 1; logger.error(...)`. `trigger_manual_festival_broadcast` returns `status='completed'`; CRM Automation dashboard (`crm_automation_dashboard.py:257-261`) shows a green `st.success`. The feature can never succeed.
- **Fix:** Use engine instances and correct kwargs, count only on real queue id:
  ```python
  from whatsapp_engine import WhatsAppEngine
  qid = WhatsAppEngine().queue_message(to_number=to, message_type="session", session_text=text, auto_send=True)
  if qid and qid > 0: stats["sent_whatsapp"] += 1
  else: stats["failed"] += 1
  # email:
  from email_engine import EmailEngine
  qid = EmailEngine().queue_email(to_email=to, subject=subj, body_html=text, email_type="festival", auto_send=True)
  ```

### 3. Rate-broadcast audience reads non-existent customer columns — every DB customer dropped from WhatsApp blasts
- **File:** `rate_broadcast_engine.py:91`
- **What's wrong:** `SELECT * FROM customers` then `r.get("mobile1", r.get("mobile2",""))`, `r.get("preferred_grade","VG30")`, `r.get("vip_tier","standard")`. Real columns are `contact` / `whatsapp_number`, `preferred_grades` (plural), and no `vip_tier`. Phone resolves to `""` for every customer; the dedup loop (`:124-133`) drops contacts with empty phone+email, so all DB customers (which have a valid `contact` but NULL email/whatsapp_number) are silently excluded.

### 4. Rate broadcast labels a GST+freight-inclusive landed cost as "Ex-Terminal | GST 18% Extra" — customer double-charges GST
- **File:** `rate_broadcast_engine.py:184` (WA) / `:237` (email)
- **What's wrong:** Broadcasts `landed_cost` = `base_price + 18% GST + freight` (`calculation_engine.py:513`) but the footer says `Ex-Terminal | GST 18% Extra`. A customer adding 18% on top over-bills ~18%, and "Ex-Terminal" is false (freight baked in). `calculate_personalized_rate` already returns the true `base_price` but the message ignores it.
- **Why silent:** Semantic error — both numbers are valid floats; surfaces only as an over-quote at the customer's end.
- **Fix:** Either display `base_price` (keep "Ex-Terminal | GST 18% Extra" truthful) **or** keep `landed_cost` and relabel "Delivered to {city}, incl. GST 18% + Freight". Do not mix the two.

### 5. Action-bar "Send Email"/"Send WhatsApp" queue rows as `status='draft'` but tell the user it will send

- **What's wrong:** `send_email_report`/`send_whatsapp_report` call `queue_email`/`queue_message` **without** `auto_send`, which defaults to `status='draft'` (`email_engine.py:423`, `whatsapp_engine.py:395`). `process_queue` only drains `'pending'`, and the WA unified-QR send path (`whatsapp_engine.py:407`) is itself `auto_send`-gated. The UI shows "Queued N — Will be sent in next processing cycle" (`action_bar.py:271`).

- **Fix:** Pass `auto_send=True` in both calls (`:505`, `:550`). If drafts are intentional, change the `action_bar.py:271/:321` copy to "Saved as draft — approve in Email/WhatsApp Setup to send."

### 6. Scheduled-share email/WhatsApp queued as `status='queued'` (never drained) + bare-except marks the batch 'sent'
- **File:** `share_automation_engine.py:182` (email) / `:201` (WhatsApp) — *merges 3 reports*
- **What's wrong:** Inserts use `status='queued'`; the only senders (`email_engine.process_queue` `:445`, `whatsapp_engine.process_queue` `:439`) select `status='pending'` and nothing promotes `queued→pending`. Compounding: `_send_email`/`_send_whatsapp` wrap everything in `try: … except Exception: pass`, yet `_execute_schedule` unconditionally calls `_track_send` which stamps `delivery_status='sent'` for the full recipient count.
- **Why silent:** INSERT succeeds (free-text status); UI reports delivered; rows sit forever.
- **Fix:** Change inserted status to `'pending'` at `:182` and `:201`. Stop swallowing: log + return a sent/failed count, and only `_track_send` recipients actually queued (record `'queued'`/`'pending'`, not `'sent'`, until `process_queue` confirms delivery).

### 7. `discussion_guidance_engine` re-parses crude/FX JSON tails, bypassing the staleness guard
- **File:** `discussion_guidance_engine.py:169` (`brent` `:182`, `usdinr` `:191`)
- **What's wrong:** `_get_market_context()` reads `tbl_crude_prices.json`/`tbl_fx_rates.json` and takes `[-1]` with no age check, instead of `get_unified_prices()` (which rejects records older than `_MAX_PRICE_AGE_DAYS=3`). Drives the customer talk-track and the FOB benchmark (`usdinr` at `:452`). Also `benchmark=="Brent"`/`pair=="USD/INR"` are exact-case matches vs unified's lowercased substring.

- **Fix:** `from market_data import get_unified_prices`; `u = get_unified_prices(); context["brent_usd"] = u.get("brent"); context["usdinr"] = u.get("usdinr")`. Delete the bespoke parsing and exact-string matching; align the `:452` `or 83.25` fallback with the unified default.

### 8. `alert_system` Brent/USD-INR/VIX computed once at import — frozen at server start, bypasses unified source
- **File:** `command_intel/alert_system.py:14`
- **What's wrong:** Module-scope `_LIVE_BRENT/_LIVE_USDINR/_LIVE_VIX = get_brent_price()/...` run once per process and feed ALT-002's "Live" message + severity branch — never refresh in the long-lived Streamlit process.
